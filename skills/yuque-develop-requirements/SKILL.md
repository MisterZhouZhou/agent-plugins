# 语雀需求提炼

## 目标

收到语雀文档链接（或本地 PRD Markdown 文件）后，按以下目标执行：

1. 使用语雀 API 拉取文档内容（本地文件则直接读取）。
2. 清洗语雀返回内容中的冗余 HTML 标签、样式和无关包裹结构，输出可读 Markdown。
3. 检测 PRD 涉及的端（后端 / PC / H5 / 小程序），由用户勾选本次要整理的端。
4. 收集并解析视觉物料（设计稿优先于原型），与 PRD 做综合分析；将 Figma 帧映射到页面清单。
5. 仅对综合分析后仍阻塞的疑问，按"依赖树 + 分批"方式向用户交互式追问，直到阻塞类疑问全部答完。
6. 按用户所选的端分别提炼对应端的技术信息（其他端专属内容不进入本次输出）。
7. 按固定模板输出"技术实现需求文档"，作为可直接驱动开发的提示词；用户选择多个端时每个端分别产出一份独立文档；每个页面的 `设计稿：` 字段尽量填入已映射的具体 Figma 地址。

## 必要输入

- 语雀文档链接，或 `repo namespace + doc slug`，或本地 PRD Markdown 文件路径
- 具备读取权限的语雀 Token（语雀链接场景）。优先使用用户级配置文件中的 Token；没有配置时再通过 `--token` 或环境变量兜底。
- 目标端：由后续「端检测与端选择」步骤确定，取值范围固定为 `后端` / `PC` / `H5` / `小程序`（可多选）；不自行假设，不推断

如果文档是私有库且当前没有可用 Token，先向用户索要 Token 再继续。

## 执行流程

### 1. 解析文档标识

- 优先从语雀链接中解析 `repo namespace` 和 `doc slug`。
- 解析失败时，再要求用户补充 `repo namespace` 和 `doc slug`。
- 输入是本地 Markdown 文件路径时，直接进入第 3 步。

### 2. 拉取并清洗文档

- 运行 `scripts/yuque_to_markdown.py`。
- 用户给的是标准语雀链接时优先使用 `--url`。
- 链接不稳定或信息不完整时改用 `--repo-namespace` 和 `--doc-slug`。
- Token 读取优先级：共享配置文件 > `--token` 参数 > 环境变量 `YUQUE_TOKEN`。
- 共享配置文件路径：`~/.agents/yuque-develop-requirements/config.json`。
- 配置文件使用简单字典格式，key 为语雀链接 owner 一级，value 为对应 Token。
- 自动匹配 Token 时只使用语雀链接 owner 一级，例如 `https://souche.yuque.com/cyp/heh0hl/doc-slug` 只用 `cyp` 匹配配置字典。
- 多团队 Token 可用 `--token-key` 指定，例如 `--token-key cyp` 或 `--token-key beijing-myye7`。
- 若用户没有指定输出文件名，使用语雀返回的 `data.title` 作为文件基名。
- 原始清洗结果文件命名规则：`{title}-原文档.md`
- 技术文档命名规则：`{title}-{端标识}技术文档.md`，端标识取值：`后端` / `PC` / `H5` / `小程序`；用户选择多个端时**每个端分别产出一份独立文档**，不合并
- 清洗过程必须**完整保留所有 Figma 链接**（含 `node-id=x-xxx` 子链接）、所有外部链接、所有代码片段，不得只保留首个链接。

示例：

```bash
python3 scripts/yuque_to_markdown.py \
  --url "https://www.yuque.com/owner/repo/doc-slug" \
  --output-dir /tmp
```

用户级配置示例：

```json
{
  "cyp": "YOUR_CYP_TOKEN",
  "beijing-myye7": "YOUR_BEIJING_MYYE7_TOKEN"
}
```

支持的链接格式包括：

- `https://www.yuque.com/owner/repo/doc-slug`
- `https://tenant.yuque.com/owner/repo/doc-slug`

### 3. 端检测与端选择

拉取并清洗文档后，**必须**先做端检测再进入信息提炼，禁止跳过。

#### 3.1 端检测（LLM 通读判断）

通读清洗后的 Markdown，识别 PRD 涉及的端，取值固定为四选：

- `后端`
- `PC`（中后台管理系统 / 桌面 Web）
- `H5`（移动端 Web / 移动端浏览器）
- `小程序`

判断依据：

- 仅识别 PRD 中**证据充分**的端（有明确页面描述、明确端标注、明确交互场景）
- **不推断**、不臆测：PRD 里没有明确说的端不列入检测结果
- 对模糊表达（"用户在设备上操作"、"移动侧"）不猜归属，交由用户在勾选阶段自行补充

#### 3.2 端选择（询问用户）

把检测结果按下方格式清晰列给用户，让用户勾选本次要整理的端：

```
检测到本 PRD 涉及以下端：
- [ ] 后端（示例证据：xxx 章节包含接口设计 / 数据表结构）
- [ ] PC（示例证据：xxx 章节有中后台审批页描述）
- [ ] H5（示例证据：xxx 章节有移动端下单流程）
- [ ] 小程序（示例证据：xxx 章节提到小程序分享）
请回复本次需要整理的端（可多选，例："H5" 或 "H5+后端"）。
```

规则：

- 只列出**检测到的**端，未检测到的端不列
- 每个端附上简短的"示例证据"（章节号或关键词），让用户核对检测是否准确
- 检测结果为 0 个端时：如实告知"未从 PRD 中检测到明确的端标注"，请用户直接告知涉及哪些端
- 用户勾选的端**不在检测结果内**时（例如检测到只有 PC，用户说要 H5）：如实告知"未检测到 H5 相关内容"，请用户确认是继续硬拉、补充信息还是终止

#### 3.3 分派至对应提炼流程

按用户勾选结果并行处理：

- 勾选包含 `PC` / `H5` / `小程序` 中任意一个或多个 → 每个端**分别**进入第 4 步（前端方法论），每个端产出一份独立技术文档
- 勾选包含 `后端` → 进入第 5 步（后端方法论），产出一份独立技术文档
- 同时勾选多个端时：不合并输出，逐一产出多份独立文档

#### 3.4 端过滤方法论（进入第 4/5 步之前必读）

按内容层次采用不同的过滤策略，避免因过滤过度伤及所选端的业务理解：

| 内容层次 | 过滤策略 | 原因 |
|--------|--------|-----|
| 页面 / 弹窗 / 交互 | **白名单**：只保留所选端的条目，其他端页面不纳入 | 页面归属端通常明确，白名单结果干净 |
| 后端接口路径 / 请求字段 / 响应字段 | **强制占位化**：无论所选端是什么，一律不落入前端技术文档，改用 `<接口路径>` / `<字段名>` / `<请求参数>` / `<响应字段>` 等占位标签；真实接口缺失时，明确要求先通过独立 API 层提供可替换 Mock | PRD 通常由产品用 AI 生成，接口和字段是示意性内容，后端实际实现的命名不一定一致，落入提示词会误导前端开发按错误命名开发；独立 API 层可降低后续接入真实接口的改动范围 |
| 业务规则 / 状态定义 / 状态流转 / 字典含义 / 时间窗口 / 可见性规则 | **黑名单**：默认全部保留，仅剔除 PRD 中显式标注"仅 PC 使用"/"仅小程序使用"等他端专属规则 | 业务语义跨端共享，产品定义可信，是前端理解需求的必要背景 |

三条硬约束：

1. **端过滤仅影响"页面/弹窗/交互层"**，其他两层与端选择无关
2. **状态枚举的含义（如"待支付/待发货/已完成"）保留**，但**字段名（如 `orderStatus`）和数值（如 `1/2/3`）不保留**，改用占位标签；例外：用户在参考上下文明确提供"已有真实接口文档"或"接口命名规则"时可使用真实命名
3. 判断某条业务规则时：问"当前所选端会不会用到这条规则"，用得到就贴到对应页面下（沿用 4.2 的分发规则）；用不到才丢

#### 3.5 视觉物料综合分析（设计稿优先）

进入疑问澄清与第 4/5 步**之前**，必须先完成视觉物料的收集、优先级判定与综合分析。禁止只读 PRD 文字就进入追问或产出。

##### 3.5.0 视觉物料优先级

按可信度从高到低使用：

1. **正式设计稿**（Figma 等，含真实页面布局、交互态、多状态帧）——**最终要实现的效果**，主依据
2. **可交互原型 / PRD 内嵌线框**——PRD 侧多为方案与原型示意；**仅当没有设计稿时**作为页面与交互主依据；有设计稿时最多作补充参考
3. **纯 PRD 文字描述**——无视觉物料时的兜底

**总原则（用户确认）**：当 PRD **已提供** Figma 或其他正式设计稿时，**页面样式与页面功能均以设计稿为主**——PRD/原型描述的是方案意图与业务背景，设计稿才是最终要实现的页面效果与交互形态。不要把 PRD 里的弹窗/布局/按钮文案/筛选等页面级描述压过设计稿。

##### 3.5.0a 综合分析分工

| 信息类型 | 主依据 | 说明 |
|--------|--------|------|
| 页面结构 / 页面形态（全屏页 vs 弹窗/抽屉）/ 字段展示 / 按钮文案 / 空态 / 多状态 UI / 布局 / 页面内交互流程 | **设计稿**（无则原型） | 有设计稿时样式与功能均跟设计；帧名与画面不一致时以画面为准 |
| 跨页面业务规则 / 准入条件 / 状态机语义 / 权限 / 时间窗口 / 互斥 / 金额计算口径 | PRD | 设计稿通常不承载完整业务规则；规则仍从 PRD 提炼并贴到对应页面 |
| PRD 与设计稿冲突 | **页面级默认跟设计稿**；仅当冲突触及跨页业务规则、准入、状态机或权限且无法从设计稿判断时，才记为阻塞类疑问 | 禁止把「PRD 写弹窗、设计是全屏页」之类页面形态问题再当成必须二选一的阻塞疑问 |

##### 3.5.0b Figma 完整功能模版 → 页面映射（硬约束）

PRD 中的 Figma 经常是**完整功能模版总入口**（只有一个文件链接或根 `node-id`），而不是每个页面已写好的子链接。此时不能只把总入口挂一次、其余页面写占位，必须做**帧 ↔ 页面**映射：

1. **收集链接**：从清洗后的 Markdown 中提取全部 Figma 链接（含 `node-id`）、原型 HTML 链接；清洗阶段已要求不得只保留首个链接。
2. **解析结构**（尽力而为）：
   - 优先用可用的 Figma 能力（如 Figma MCP、可访问的文件节点树）读取帧名 / 页面名 / 状态名
   - 无法程序化打开时：根据 PRD 内嵌的设计说明、帧命名约定、截图标注做映射；仍不够则在疑问澄清中向用户要「页面 → node-id」对照或导出图
   - 不要因为「打不开 Figma 预览」就放弃映射：至少把总入口与 PRD 页面清单建立对应关系，能定位到的子帧必须写成具体链接
3. **对齐页面清单**：与 4.1 将产出的页面 / 弹窗 / 状态分支一一对应（如「订单详情-更多菜单」「开票填写-个人/企业」「详情-开票中/已开票/失败」）。
4. **写入产出**（见 4.7 / 6.1）：
   - 每个页面 / 弹窗 / 状态分支的 `设计稿：` 行填**最具体**的 Figma 子链接（带 `node-id`）
   - PRD 已写明的子链接必须原样落到对应页面，禁止只留总入口
   - 映射成功的页面**禁止**再写 `<设计稿地址：xxx场景>`
   - 仅当某页确实对不上任何帧时，才对该页使用占位，并可附一行总入口作参考
5. **有设计稿时**：设计稿已能确定的**页面样式与页面功能**（结构 / 交互形态 / 文案 / 筛选是否存在 / 全屏还是弹窗等），**直接采用设计稿**，不要再当作阻塞类疑问去问用户。

##### 3.5.0c 无设计稿时的原型与占位

- 仅有原型：用原型补 UI/交互，`设计稿：` 可填原型链接，建议同时写 `参考原型：` 并注明「依据原型，可能与最终设计有差」
- 设计稿与原型都没有：各页使用 `<设计稿地址：xxx场景>` 占位，不硬猜布局

#### 3.6 疑问澄清（交互式追问）

进入第 4/5 步组织技术文档**之前**，必须在 **3.5 视觉物料综合分析完成之后**，扫描 PRD + 设计稿/原型中仍需澄清的疑问点，以交互式追问的方式**分批**向用户确认。禁止跳过；也禁止把所有疑问一次性扁平化打包；禁止把设计稿/原型已能回答的问题再问一遍。

##### 3.6.1 疑问分类

按是否影响最终技术文档的形态，分两类，只有阻塞类才进入追问流程：

- **阻塞类疑问（必须问）**：用户答不同选项会导致**最终技术文档产出不一样**。典型场景：
  - PRD 中同一功能给出多种可行方案但未明确选择（如"游客下单 or 必须登录"）
  - PRD 内部逻辑矛盾（如"字段 A 必填但示例里没填"、"状态 X 可流转到 Y 但流程图里没有这条线"）
  - 同一交互存在多种可行形式且 **PRD 与设计稿均未明确**（如"列表分页方式"）
  - 影响跨页业务分支、状态机语义、权限、准入条件的方案分歧（且设计稿无法裁决）
  - Figma 完整模版无法可靠映射到某关键页面且会改变页面清单，且用户未提供其他视觉依据
  - **不要**把「PRD 原型与设计稿页面形态不一致」列为阻塞类——有设计稿时页面样式与功能默认跟设计
- **提醒类疑问（不问，占位兜底）**：用户答不同选项**只是补一个具体数值**，不改变文档结构。典型场景：
  - 后端接口路径、字段名（用占位标签 `<接口路径>` `<字段名>`）
  - 项目内文件路径、路由路径（用占位标签 `<页面创建路径>` `<路由模块路径>`）
  - 某页设计稿子帧确实缺失且不影响页面拆分（用占位标签 `<设计稿地址：xxx场景>`，有总入口则同时保留总入口链接）
  - 后端未提供的具体数值/枚举值（写 `暂无` 或 `待确认`）

**判断标准**：用户答不同选项，最终产出的技术文档会不会**长得不一样**（章节结构、页面数量、状态数量、流程分支不同）？会 → 阻塞类；不会 → 提醒类。设计稿/原型已给出答案的，直接采用，不进入追问。

##### 3.6.2 疑问依赖树（构建规则）

列出所有阻塞类疑问后，**内部构建疑问树**，禁止扁平化：

- 对每个疑问判断是否存在**前置疑问**（当且仅当前置疑问某个答案下本疑问才存在）
  - 有前置 → 是**子疑问**，必须等前置回答后才决定是否问
  - 无前置 → 是**独立疑问**，可与其他独立疑问同批询问
- **互斥疑问识别**：Q_A 和 Q_B 只有其一会真正被问出（依赖同一个前置的不同答案）→ 两者**不允许同批问**
- **去重**：多个页面共享同一疑问 → 只问一次，答案应用到所有相关页面

##### 3.6.3 分批询问策略

按疑问树**逐层追问**，每批只问当前层的独立疑问：

1. 从疑问树中提取"当前就绪"的独立疑问（无前置 或 前置已解答）
2. 同一批**合并询问**，一次问出（一般不超过 5 个/批，超过就再拆一批）
3. 用户回答后：
   - **剪枝**：删除被答案排除的分支（互斥疑问的另一支不再问）
   - **展开**：新暴露的下一层子疑问加入下一批的候选队列
4. 回到第 1 步，直到疑问树为空

##### 3.6.4 询问格式模板

每批询问用固定模板产出，让用户能对应回 PRD / 设计稿：

```
本轮有 N 个独立疑问需要确认：

Q1【归属：xxx 页面 / 组件】
   触发原因：PRD 第 X 章节 "xxx" / 设计稿帧 "yyy" 存在 xxx 问题（多方案 / 矛盾 / 不明确 / PRD与设计稿冲突）
   候选选项：
     A. 方案 A（含简短后果说明）
     B. 方案 B（含简短后果说明）
     C. 其他（请补充）

Q2【归属：xxx】
   触发原因：...
   候选选项：...
```

##### 3.6.5 硬约束

1. **禁止合并互斥疑问**（如"游客下单方案"和"必须登录方案的登录浮层设计"不能同批问）
2. **禁止一次性打包所有疑问**（必须按依赖树分批）
3. **禁止在候选选项旁标推荐**（避免暗示用户，除非用户主动要求给建议）
4. **禁止把提醒类疑问混入阻塞类追问**（占位标签能兜住的一律不问）
5. **禁止把设计稿/原型已能确定的 UI/交互再当成阻塞类去问**
6. **用户答完全部阻塞类疑问前，禁止进入第 4/5 步产出技术文档**
7. 用户明确回答"跳过 / 用占位兜底 / 我也不确定" → 该疑问降级为提醒类，写占位标签或 `待确认`
8. **未完成 3.5 视觉物料综合分析前，禁止进入本步追问**

### 4. 提炼前端相关信息（核心方法论）

前端提炼的目标是**生成可直接驱动开发的页面级提示词**，不是 PRD 的摘要或复述。必须按以下三步执行：

#### 4.1 第一步：抽取页面 / 弹窗 / 公共组件清单

通读 PRD，并对照 3.5 已收集的设计稿/原型帧，列出**所有需要前端实现的页面、弹窗、抽屉、公共组件**。判断标准：

- 任何"新页面"、"新增入口"、"新增列表"、"新增详情"、"新增标签页" → 是一个**页面**
- 任何"弹框"、"弹窗"、"抽屉"、"二次确认"、"成功提示" → 是一个**页面或弹窗**
- 任何"在多个地方复用的元素"，如表单组件、抬头组件、订单卡片 → 是一个**公共组件**
- PRD 章节号（6.1、6.2、6.3...）**不是**组织单位，只是提炼来源

最终清单形如：
- 公共组件：开票抬头组件、订单卡片组件、...
- 页面：单张开发票页面、批量开发票页面、确认开票信息页面、我的开票列表页、开票详情页、...

#### 4.2 第二步：把 PRD 散落规则"分发"到对应页面

PRD 通常按"功能维度"组织（入口规则、字段规则、状态机、批量规则、互斥规则、回调状态...），不按页面。提炼时必须把这些规则**拆开并贴到对应页面下**：

- "表单字段级联规则" → 贴到**表单所在的弹窗/页面**
- "二次确认文案" → 贴到**二次确认弹窗**
- "时间窗口/可见性规则" → 贴到**入口所在页面**
- "状态颜色/失败原因展示" → 贴到**详情页或列表页**
- "重试入口逻辑" → 贴到**详情页**
- "STS 回调状态枚举" → 贴到**展示该状态的页面**（通常是详情/列表）

同一条规则可以同时贴在多个页面下，只要每个页面用得到。

#### 4.3 第三步：每个页面/组件按统一结构产出

每个页面/组件下分条目编号产出，每条尽量包含：

1. **页面定位**：路径、路由配置、设计稿、UI 还原要求、导航形式
2. **页面结构与字段**：分区域；每个字段必须给出：字段名 | 数据类型 | 使用组件（input / select / radio / checkbox / datepicker / upload / 自定义组件等） | 必填或选填 | 校验规则 | 数据来源 | 是否只读
3. **校验规则**：字段校验、跨字段校验、提交校验
4. **交互**：每个按钮文案 + 点击行为 + 跳转目标 + 弹窗联动；自动行为（自动填充/自动计算/自动显隐/自动关闭）
5. **接口占位与 Mock**：根据页面动作识别查询、详情、提交、删除、上传等接口调用场景，写出动作、接口路径占位、调用时机、成功/失败后的行为；真实接口未提供时，要求先在独立 API 请求层提供 Mock，页面和组件只能通过统一 API 方法调用，禁止直接写死 Mock 业务数据。Mock 与真实请求保持一致的 Promise/异步边界，并覆盖 loading、成功、空数据和失败状态；后续接入真实接口时，原则上仅替换 API 实现、请求参数和响应字段适配，不修改页面交互和业务流程。所有接口必须**贴在使用它的页面/组件下**，禁止单独建顶层接口章节。**即使 PRD 中已给出接口路径/字段名也不落入前端技术文档**（PRD 通常由产品用 AI 生成，接口和字段是示意性内容，后端实际实现命名可能不一致），一律改用 `<接口路径>` / `<字段名>` / `<请求参数>` / `<响应字段>` 占位标签；例外情况见 3.4 硬约束第 2 条
6. **异常态**：缺省页、空数据、加载失败、缺省页文案（含换行符 `\n` 需要明确）
7. **状态分支**：若页面承载多类型/多状态，逐条列出每个组合的设计稿链接

#### 4.4 占位标签规则（重要）

PRD **没有提供**而前端开发必须知道的信息，统一使用占位标签写法，**不要写"暂无"**（"暂无"太弱，开发会忽略；占位标签明确提醒"需要用户补"）。常用占位标签：

- `<设计稿地址：xxx场景>` — 仅当该页确实无可用 Figma/原型映射时使用；有映射时必须写真实链接
- `<页面创建路径>` — 项目内的文件路径，如 `src/views/xxx/yyy`
- `<路由模块路径>` — 项目内的路由模块文件
- `<路由总入口>` — 项目内的路由总入口文件
- `<接口路径>` — 后端接口路径
- `<字段名>` — 接口字段命名
- `<参考实现路径>` — 项目内可参考的现有实现路径
- `<主题色样式变量>` — 项目样式变量
- `<其他项目约束>` — 用户的额外项目约束

PRD **已经提供**的链接/路径/字段必须**原样保留**，绝不能替换成占位标签。

**例外（重要）**：以下两类内容**不适用**"原样保留"，必须占位化：

- **后端接口路径**（如 `/api/xxx/yyy`）：PRD 由 AI 生成，接口路径通常不是后端真实实现，一律替换为 `<接口路径>`
- **后端字段名 / 请求参数名 / 响应字段名**（如 `orderStatus`、`refundStatus`）：同上，一律替换为 `<字段名>` / `<请求参数>` / `<响应字段>`

**仅当**用户在 `# 参考上下文` 明确提供了"已有真实接口文档"或"接口命名规则"时，才可使用真实字段名；否则一律占位。业务语义（状态含义、状态流转、业务规则、字典枚举的文案）不受此例外影响，仍需保留。

**接口缺失时的可替换 Mock 硬约束**：

- 不追问具体接口路径、请求字段或响应字段；这些属于提醒类缺失，不阻塞前端技术文档产出。
- Mock 必须位于独立 API 请求层，页面和组件不得直接写死 Mock 业务数据，也不得在业务代码中散落 Mock 开关判断。
- 页面始终按真实异步请求方式调用 API，并处理 loading、成功、空数据和失败状态。
- 真实接口提供后，原则上只替换 API 实现、请求参数和响应字段映射；页面交互和业务流程保持不变。
- 不规定具体 Mock 工具、目录名或框架，由目标项目现有技术栈决定实现方式。

#### 4.5 不输出的内容（去噪）

以下内容**不要**出现在前端技术文档中：

- "一句话摘要"（PRD 复盘语气，开发不需要）
- "用户故事"、"业务背景"、"目标 / KPI"（开发不消费）
- "术语定义"（如开票情况 / 开票状态枚举完整定义，应下沉到使用该枚举的页面里）
- "全文待确认项汇总"（应贴到对应页面里）
- "顶层独立接口清单 / 独立的接口章节"（必须嵌入每个页面的接口占位里，让接口跟着页面走，避免误调接口；这是硬约束，不可妥协）
- "状态机 / 用户流程图"的纯文字复述（已在原文档里，不复述）
- "Non-goals / 不做场景"（除非直接影响某个页面的显隐，否则不出现）

#### 4.6 参考上下文的填充规则

`# 参考上下文` 是项目代码锚点，不是 PRD 摘要：

- 用户明确提供的代码路径、组件参考、接口文件位置、样式变量、命名约定 → 原样保留
- 用户未提供时 → 使用占位标签 `<项目代码上下文：用户未提供时保留此占位标签，由用户后续补充>`，并附若干形如 `<popup组件参考路径>` 的具体子占位
- **绝不能**把 PRD 摘要塞进 `# 参考上下文`

#### 4.7 设计稿处理规则

设计稿是**分析输入**也是**产出字段**。处理顺序与 3.5 一致：先综合分析并完成帧映射，再写入各页面的 `设计稿：` 行。

**优先级**：正式设计稿（Figma）> 可交互原型 > 纯文字。有 Figma 时不得只用原型充当主设计稿。

##### 4.7.1 有 Figma 时（含「完整功能模版」总入口）

- 每个页面 / 弹窗 / 公共组件 / 状态分支的 `设计稿：` 必须填**最具体**的子链接（含 `node-id`），不要只贴总入口敷衍所有页面
- PRD 已写出的页面级 / 状态级子链接 → **原样**落到对应条目，禁止改成占位
- PRD 只给了完整功能模版总入口 → 按 3.5.0b 完成帧 ↔ 页面映射后，把映射到的具体地址写入对应页面；映射成功则**禁止**再写 `<设计稿地址：xxx场景>`
- 多状态 / 多类型页面：在「状态分支」下**逐条**列出每个组合的 Figma 子链接，不能只写一个「通用主态」占位
- 可选：同一条目下可额外保留 `完整设计稿总入口：` 一行，但**不能**用总入口替代本页具体链接
- 有原型时：原型可写在 `参考原型：` 作补充，**不能**在已有 Figma 映射的情况下把 `设计稿：` 写成原型链接或占位

##### 4.7.2 无 Figma、仅有原型

- `设计稿：` 可填原型链接（或写 `参考原型：`），并注明依据原型、可能与最终设计有差
- 不要假装存在 Figma 子帧

##### 4.7.3 设计稿与原型都没有

- 使用占位标签 `<设计稿地址：xxx场景>`，不要写"暂无"或删除该行
- 占位标签的作用是**提醒后续可能补充**，不是强制必须有设计稿
- **禁止**在「PRD 已有可用 Figma 总入口或子链接」时仍对本可映射的页面统一输出占位（这是错误，不是兜底）

### 5. 提炼后端(Java)相关信息

**仅当用户在第 3 步的端选择中勾选了 `后端` 时进入本步骤。**

后端文档不受"端过滤"限制，产出目标是完整的后端实现需求文档（服务/接口/数据/流程），不裁剪。

优先关注以下内容：

- 服务类、Controller、Service、Mapper/Dao 层级结构
- 接口路径、请求方法、请求参数、响应结构
- 业务逻辑处理流程、校验规则、异常处理
- 实体类、字段定义、数据类型、默认值
- 数据库表结构、关联关系、索引设计
- 枚举类、字典数据、状态流转
- 事务处理、缓存策略、日志记录
- 第三方服务调用、消息队列、定时任务
- 用户额外提供的参考代码路径或已有接口实现方式

不要虚构源文档中不存在的业务逻辑、接口字段或状态枚举。

### 6. 按模板输出技术实现文档

按用户第 3 步选择的端，**逐个端独立产出**（一个端一份文档，不合并）。

模板选择：

- 端为 `PC` / `H5` / `小程序`：统一使用 `assets/frontend_requirement_template.md`（前端各端共用模板）
- 端为 `后端`：使用 `assets/backend_requirement_template.md`

文件命名（沿用第 2 步）：`{title}-{端标识}技术文档.md`，端标识取值 `后端` / `PC` / `H5` / `小程序`。

**多端并选示例**：用户勾选 `H5` + `后端`，则本次产出两份独立文档：
- `{title}-H5技术文档.md`（基于前端模板，只含 H5 归属的页面/交互，含 3.4 端过滤方法论产出的业务规则）
- `{title}-后端技术文档.md`（基于后端模板，完整后端需求，不受端过滤限制）

#### 6.1 前端输出规则（与第 4 步配套）

- `# 参考上下文`：按 4.6 规则填充，禁止填 PRD 摘要。
- `# 功能需求` 下的二级标题**必须按页面/弹窗/公共组件**组织，**禁止**按 PRD 章节号（6.1/6.2/...）组织。
- 公共组件单独成段，放在 `## 公共组件` 下，作为后续页面引用对象。
- 每个页面/组件下按 4.3 结构分条编号产出。
- **设计稿字段（硬约束）**：
  - 所有 PRD 中出现的 Figma 子链接（含 `node-id`）必须落到对应页面 / 状态分支，丢失即视为错误
  - 经 3.5 映射得到的页面级 Figma 地址必须写入该页 `设计稿：`，不得再用 `<设计稿地址：…>` 占位
  - 禁止「全文只挂一个 Figma 总入口 + 各页全是占位」的写法
  - 有 Figma 时 `设计稿：` 优先 Figma；原型仅作 `参考原型：` 补充
- PRD 未提供且映射后仍缺失的项，才使用 4.4 的占位标签；禁止写"暂无"或"待确认"。
- 页面结构 / 交互 / 文案等已从设计稿综合分析得到的内容，应写入对应条目，不要因「PRD 文字没写细」就省略或一律占位。
- 保留文末 `## 工作流程` 的协作约束。

#### 6.2 后端输出规则

- `# 参考上下文` 只承接用户额外明确提供的上下文（参考代码路径、已有接口、命名规则）。用户没有提供时填写 `暂无`。
- `# 功能需求` 下的二级标题尽量复用原始需求标题。
- 接口类需求优先拆成：接口路径、请求参数、响应结构、业务逻辑、异常处理。
- 数据类需求优先拆成：表结构、字段定义、关联关系、索引设计。
- 服务类需求优先拆成：服务职责、业务流程、校验规则、事务处理。
- 用户已提供接口文档时按模板整理；只提供部分时只填已知部分，其余写 `暂无`。
- 用户提供的"字段映射 / 状态枚举 / 字典类型 / 请求示例"原样保留命名，不自行改写。
- 无法从文档确认的结论显式写"待确认"或"暂无"，不推断。
- 当某编号条目下需细分子场景时使用"编号项 + 次级短横线列表"形式，不在一段里堆。

## 输出质量要求

最终技术文档应满足：

- 仅输出 Markdown
- 保留原业务意图，改写成技术可执行语言
- 前端按页面/组件分组，后端按原需求标题分组
- 缺失上下文 / 接口 / 字段 / 状态时：前端使用占位标签，后端写 `暂无` 或 `待确认`
- PRD 已提供的链接、路径、字段必须原样保留
- 有 Figma（含完整功能模版）时：各页面 `设计稿：` 应为映射后的具体地址，而不是清一色占位
- 前端提炼须综合 PRD + 设计稿（无设计稿再用原型）；设计稿已覆盖的信息不重复追问
- 前端文档可直接作为"先确认需求，再拆任务，再开发"的提示词输入

## 调试

如果语雀 API 返回 `404`，优先检查：

- Token 是否有私有知识库读取权限
- `repo namespace` 和 `doc slug` 是否完全正确
- 请求是否带了 `raw=1`
- 是否传了 `User-Agent`
